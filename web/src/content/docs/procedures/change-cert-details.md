## Purpose

Apply a change to the certificate's identity or issuance parameters — such as adding or removing
Subject Alternative Names, changing the key type, or switching the ACME profile — and force a fresh
certificate from the CA that reflects the new configuration.

## Scope

Covers changes to any of:

- `[cert] hostname`, `[cert] sans`, `[cert] ip_sans`
- `[cert] key_type`, `[cert] reuse_key`
- `[acme] profile`, `[acme] challenge`

Does **not** cover switching to a different CA (see SC-OPS-006 when available) or revoking the
current certificate before reissuing (see SC-OPS-005 when available).

## Prerequisites

- syscert is already installed and the current certificate is valid.
- You know the new values you intend to set — consult [Configuration](/docs/configuration/) for the
  allowed keys and their constraints (e.g. `ip_sans` forces the challenge to `http-01`/`tls-alpn-01`;
  private IPs require an internal CA).
- Root access to edit `/etc/syscert/syscert.toml`.

## Procedure

**1. Edit the configuration.**

```sh
sudo vi /etc/syscert/syscert.toml
```

Make the desired change. Example — adding an IP SAN:

```toml
[cert]
hostname = "host.example.com"
sans     = ["api.example.com"]
ip_sans  = ["10.0.1.5"]          # forces challenge to http-01 or tls-alpn-01
```

See [Configuration → `[cert]`](/docs/configuration/#cert--certificate-subject) for the full key
reference and constraints.

**2. Validate the config offline.**

```sh
sudo -u syscert syscert dry-run --config-only
```

This catches structural problems, unsupported combinations, and CA capability mismatches before any
network call is made. Fix all reported errors before continuing.

**3. Force a new ACME order.**

```sh
sudo -u syscert syscert renew --force
```

`--force` bypasses the expiry check and places a new order from the current config, issuing a fresh
certificate and writing it to the store (`/var/lib/syscert/`). This step is required because the
timer's automatic `ensure`/`renew` is **expiry-driven only** — it does not detect or act on config
changes.

A fresh keypair is generated by default (`reuse_key = false`). The old certificate is overwritten in
the store; if you have `[store] archive_keep` set, the previous set is snapshotted first.

**4. Distribute to configured targets.**

```sh
sudo -u syscert syscert distribute
```

`renew --force` writes the store but does not deliver to the paths in your `[[distribute]]` blocks —
the separate `distribute` step does. After this, each target path holds the new certificate.

## Verification

Confirm the new certificate contains the expected SANs:

```sh
openssl x509 -in /var/lib/syscert/cert.pem -noout -text | grep -A1 "Subject Alternative Name"
```

Expected output (example — adjust for your configured names/IPs):

```
X509v3 Subject Alternative Name:
    DNS:host.example.com, DNS:api.example.com, IP Address:10.0.1.5
```

Confirm the distributed copies were updated:

```sh
openssl x509 -in /etc/nginx/tls/fullchain.pem -noout -enddate   # adjust to your path
```

The `notAfter` date should reflect the newly issued certificate.

## Rollback / recovery

The procedure issues a fresh keypair and certificate each time. To revert:

1. Restore the previous `syscert.toml` (from a backup or version control).
2. Run `renew --force` again to reissue from the original config:

```sh
sudo vi /etc/syscert/syscert.toml    # restore previous config
sudo -u syscert syscert renew --force
sudo -u syscert syscert distribute
```

The CA will issue a new certificate matching the restored config. The previous certificate is not
automatically revoked — do so explicitly if required (see SC-OPS-005 when available).
